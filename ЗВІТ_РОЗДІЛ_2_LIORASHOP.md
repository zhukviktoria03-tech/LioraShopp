# РОЗДІЛ 2. РОЗРОБКА FULLSTACK-ЗАСТОСУНКУ НА PAYLOAD CMS ТА TYPESCRIPT (ГУСАРОВ, ЮРЧИШИН)

## Вступ до розділу

У межах виконання практичної роботи було спроєктовано та реалізовано Fullstack вебзастосунок **«LioraShop»**. Проєкт розроблено у формі промо-лендінгу (сайту-візитки) для бренду натуральної органічної косметики ручної роботи. 

Попередня частина комплексної системи була виконана мовою Python з використанням фреймворку Django. Метою даного завдання з дисципліни «Розробка застосунків на JavaScript/TypeScript» було створення легкої, динамічної, візуально привабливої презентаційної сторінки, яка знайомить потенційного покупця з філософією бренду, наочно аргументує переваги органічного догляду над масмаркетом та скеровує клієнта на основний Django-магазин для перегляду повного каталогу й оформлення замовлення зі знижкою.

Дизайн виконано в ніжній пастельній колірній гамі з поєднанням теплого кремового фону (`#FBF9F5`), шавлієвого зеленого (`#6B8E73`), ніжно-рожевого (`#E28D97`) та м'якого вершково-жовтого відтінків (`#F7E7A9`), що підкреслює чистоту, природність та екологічність продукції.

## 2.1. Архітектура та Payload CMS: монорепозиторій, конфігурація Payload (колекції, типи блоків, медіа), хмарна БД та кастомні API-ендпоінти

### 2.1.1. Монорепозиторна структура проєкту

Для спрощення розробки, стандартизації конфігурацій та незалежного розгортання було обрано архітектуру монорепозиторію. У кореневому каталозі проєкту розташовано маніфест `package.json`, який керує спільними скриптами, а сам код розділено на два ізольовані модулі:
1. `/cms` — бекенд-застосунок на основі Headless CMS системи **Payload CMS 3** та Next.js;
2. `/frontend` — швидка клієнтська частина, зібрана за допомогою інструменту **Vite** з використанням ванільного **TypeScript** та ES-модулів.

Така структура дає змогу розробнику запускати сервіси паралельно або окремо, налаштовувати різні порти локального середовища (`3000` для CMS та `5173` для фронтенду) та задавати незалежні параметри кореневої директорії (Root Directory) під час деплою на Vercel.

```text
liorashop-monorepo/
├── package.json
├── .gitignore
├── README.md
├── cms/                 # Бекенд: Payload CMS + Next.js
│   ├── src/
│   │   ├── payload.config.ts
│   │   ├── collections/ # Схеми таблиць (Users, Media, Pages)
│   │   ├── globals/     # Наскрізні налаштування (Header, Footer)
│   │   └── app/api/     # Кастомні ендпоінти (/api/common, /api/page)
│   └── package.json
└── frontend/            # Фронтенд: Vite + TypeScript
    ├── src/
    │   ├── main.ts
    │   ├── types/       # Опис типів (Type Aliases, Unions, Intersections)
    │   ├── blocks/      # Шаблонізація блоків лендінгу
    │   ├── services/    # Асинхронний шар роботи з API та Fallback Data
    │   └── styles/      # Пастельна палітра LioraShop
    ├── index.html
    └── package.json
```

### 2.1.2. Конфігурація Payload CMS та підключення хмарної БД Neon PostgreSQL

Payload CMS генерує адміністративну панель керування контентом автоматично на основі файлів конфігурації TypeScript, що усуває необхідність ручного верстання форм введення.

Для збереження даних обрано керовану хмарну реляційну СУБД **PostgreSQL** на платформі **Neon**. Оскільки серверлес-середовище Vercel має непостійне дискове сховище (ephemeral storage), використання зовнішньої хмарної бази даних є обов'язковою умовою для збереження публікацій між сесіями. Підключення реалізовано за допомогою офіційного адаптера `@payloadcms/db-postgres` у режимі Connection Pooling (пул з'єднань), що оптимізує навантаження при великій кількості одночасних безсерверних запитів:

```typescript
// cms/src/payload.config.ts
import { buildConfig } from 'payload'
import { postgresAdapter } from '@payloadcms/db-postgres'
import { lexicalEditor } from '@payloadcms/richtext-lexical'
import { Users } from './collections/Users'
import { Media } from './collections/Media'
import { Pages } from './collections/Pages'
import { Header } from './globals/Header'
import { Footer } from './globals/Footer'

export default buildConfig({
  admin: {
    user: Users.slug,
  },
  collections: [Users, Media, Pages],
  globals: [Header, Footer],
  editor: lexicalEditor({}),
  secret: process.env.PAYLOAD_SECRET || 'liorashop_dev_secret_key',
  db: postgresAdapter({
    pool: {
      connectionString: process.env.DATABASE_URL || '',
    },
  }),
  cors: ['http://localhost:5173', 'http://localhost:3000', process.env.FRONTEND_URL || ''].filter(Boolean),
})
```

### 2.1.3. Схеми колекцій (Collections), типи блоків та Globals

Структура даних LioraShop будується на таких сутностях:

1. **Колекція `Users`**: автентифікація адміністраторів та редакторів контенту із розмежуванням ролей (`admin`, `editor`).
2. **Колекція `Media`**: збереження та оптимізація завантажених фотографій косметичних засобів (генерація мініатюр 300x300 та карток 600x600).
3. **Колекція `Pages` (Конструктор блоків)**: динамічна сторінка із полем `slug` (для головної сторінки вказується `/`) та масивом `layout` типу `blocks`. До складу конструктора включено 7 типів блоків:
   - `hero` — головний банер, переваги у цифрах, заклик до переходу в Django;
   - `whyUs` — таблиця порівняння натуральної косметики LioraShop із промисловим масмаркетом;
   - `benefits` — принципи якості (органіка, Cruelty-Free, дерматологічний контроль);
   - `productsShowcase` — вітрина топових засобів (крем «Ніжна Роса», вітамінна сироватка тощо) із кнопками переходу на сторінку товару в Django;
   - `reviews` — відгуки реальних покупців з оцінками;
   - `faq` — відповіді на поширені запитання у формі акордеону;
   - `cta` — промокод `LIORAVIBE` на знижку -15% та перехід до головного магазину.
4. **Глобальні сутності (Globals) `Header` та `Footer`**: наскрізні налаштування сайту (логотип, слоган, пункти навігації, номер гарячої лінії, посилання на головний Django-магазин, копірайт та соціальні мережі).

### 2.1.4. Кастомні API-ендпоінти (`/api/common`, `/api/page?path=`)

Стандартний REST API Payload CMS повертає глибоко вкладені об'єкти з метаданими та системними полями Lexical редактора, що ускладнює парсинг на клієнті. Для оптимізації трафіку та зручності фронтенду було розроблено власні серверні маршрути (Route Handlers) у Next.js App Router:

- **`GET /api/common`**: формує чистий JSON-об'єкт із даними шапки та підвалу сайту, автоматично додаючи заголовки CORS (`Access-Control-Allow-Origin: *`).
- **`GET /api/page?path=/`**: знаходить документ у колекції `pages` за параметром `path`, перетворює масив блоків у плоску структуру із полем `type` замість `blockType` та віддає клієнту готовий масив для ітерування.

```typescript
// cms/src/app/api/page/route.ts
export async function GET(request: NextRequest) {
  const { searchParams } = new URL(request.url)
  const pathParam = searchParams.get('path') || '/'
  const payload = await getPayload({ config })

  const result = await payload.find({
    collection: 'pages',
    where: { slug: { equals: pathParam } },
    limit: 1,
  })

  if (!result.docs.length) {
    return NextResponse.json({ error: 'Сторінку не знайдено' }, { status: 404 })
  }

  const pageDoc = result.docs[0]
  const cleanBlocks = (pageDoc.layout || []).map((block: any) => {
    const { blockType, ...rest } = block
    return { type: blockType || block.type, ...rest }
  })

  return NextResponse.json({
    title: pageDoc.title,
    slug: pageDoc.slug,
    blocks: cleanBlocks,
  })
}
```

## 2.2. Клієнтська частина та стани UI: асинхронні запити до API, шаблонізація блоків, адаптивна верстка, обробка станів (завантаження / помилка / готовність)

### 2.2.1. Модульний підхід на Vite та асинхронні запити

Фронтенд побудовано за модульним принципом на чистому TypeScript без важких сторонніх UI-фреймворків. Збірник **Vite** забезпечує швидку збірку, миттєве гаряче оновлення модулів (HMR) та оптимізацію кінцевих ресурсів у папку `dist/`.

Взаємодія з бекендом реалізована в сервісному модулі `src/services/api.ts`. Використовується нативний асинхронний метод `fetch()` із підтримкою таймаутів через `AbortController` та обгорткою у блок `try...catch` для безпечного перехоплення мережевих помилок.

### 2.2.2. Обробка трьох станів користувацького інтерфейсу (UI States)

Для забезпечення якісного користувацького досвіду (UX) додаток керує трьома основними станами:

1. **Стан завантаження (`loading`)**: під час відправки паралельних запитів `Promise.all([fetchCommonData(), fetchPageData('/')])` користувач бачить брендований анімований спінер із квіткою 🌸 та написом «Завантажуємо природну красу...».
2. **Стан помилки (`error`)**: у разі збою мережі або недоступності сервера застосунок не падає з білим екраном. Відображається інформативна картка з поясненням ситуації, кнопкою **«Спробувати знову»** (`Retry`) та кнопкою **«Увімкнути демо-режим»** (Fallback mode), що активує вбудовані статичні дані.
3. **Стан готовності (`ready`)**: після успішного отримання JSON-відповіді запускається генерація шапки, блоків та футера у DOM-дерево.

### 2.2.3. Початковий екран вибору ролі (Role Modal / Portal)

Відповідно до технічного завдання, при першому відкритті вебзастосунку користувача зустрічає презентаційне модальне вікно **«LioraShop»** із вибором режиму демонстрації:
- **«Я Користувач» (Клієнт)** — відкриває промо-лендінг із переглядом переваг натуральної косметики, каталогом і посиланнями на Django;
- **«Я Адміністратор»** — надає пряме посилання на захищену панель керування контентом Payload CMS (`http://localhost:3000/admin`).

У правому верхньому кутку сторінки зафіксовано плаваючий віджет (Pill Widget), який показує поточну активну роль і дозволяє у будь-який момент повернутися до початкового вибору чи перейти в адмінку.

### 2.2.4. Шаблонізація блоків та диспетчер рендерингу

Усі секції лендінгу винесені в окремі модулі в директорії `src/blocks/`:
- `HeroBlock.ts`, `WhyUsBlock.ts`, `BenefitsBlock.ts`, `ProductsShowcaseBlock.ts`, `ReviewsBlock.ts`, `FaqBlock.ts`, `CtaBlock.ts`.

Головний диспетчер `src/render/renderBlocks.ts` ітерує масив блоків, аналізує поле `type` кожного блоку за допомогою конструкції `switch...case` та викликає відповідну функцію генерації HTML:

```typescript
// frontend/src/render/renderBlocks.ts
export function renderBlocks(blocks: PageBlock[]): string {
  return blocks
    .map((block) => {
      switch (block.type) {
        case 'hero': return renderHeroBlock(block)
        case 'whyUs': return renderWhyUsBlock(block)
        case 'benefits': return renderBenefitsBlock(block)
        case 'productsShowcase': return renderProductsShowcaseBlock(block)
        case 'reviews': return renderReviewsBlock(block)
        case 'faq': return renderFaqBlock(block)
        case 'cta': return renderCtaBlock(block)
        default: return ''
      }
    })
    .join('\n')
}
```

Усі динамічні текстові змінні екрануються допоміжною функцією `escapeHtml()` для захисту від XSS-атак. Після монтажу HTML у DOM підключаються інтерактивні обробники подій, зокрема акордеон у блоці FAQ.

### 2.2.5. Адаптивна верстка та фірмова палітра

Стилі описано у файлі `src/styles/main.css`. Використано CSS-змінні (CSS Custom Properties), гнучку розмітку Flexbox та CSS Grid. Завдяки медіа-запитам (`@media (max-width: 900px)`, `@media (max-width: 600px)`) та адаптивним шрифтам `clamp()` лендінг коректно підлаштовується під будь-які пристрої (смартфони, планшети, ультрабуки).

## 2.3. Типізація на TypeScript: створення типів для структури сторінки та її блоків, використання Type Aliases, Union Types та Intersection Types для опису різних типів даних, типізація функцій і об'єктів, типізація даних, отриманих через API

Файл `src/types/index.ts` містить комплексну систему типізації, яка демонструє всі ключові можливості сучасної системи типів TypeScript:

### 2.3.1. Типові псевдоніми (Type Aliases)

Псевдоніми створені для опису обмежених наборів примітивних значень та перелічуваних типів:

```typescript
export type UserRole = 'guest' | 'admin' | 'editor'
export type UIState = 'loading' | 'error' | 'ready'
export type BlockType = 'hero' | 'whyUs' | 'benefits' | 'productsShowcase' | 'reviews' | 'faq' | 'cta'
export type HttpMethod = 'GET' | 'POST' | 'PUT' | 'DELETE'
export type ID = string | number
```

### 2.3.2. Перетинні типи (Intersection Types, оператор `&`)

Intersection Types використано для забезпечення наслідування властивостей. Базовий тип `BaseBlock` містить загальні поля для всіх блоків (`id`, `type`, `order`), а конкретні блоки розширюють його специфічними полями:

```typescript
export type BaseBlock = {
  id?: string
  type: BlockType
  order?: number
}

export type Timestamped = {
  createdAt?: string
  updatedAt?: string
}

// Поєднання BaseBlock із даними блоку Hero
export type HeroBlock = BaseBlock & {
  type: 'hero'
  badge?: string
  title: string
  subtitle: string
  primaryButtonText: string
  primaryButtonUrl: string
  secondaryButtonText?: string
  secondaryButtonUrl?: string
  stats?: Array<{ value: string; label: string }>
}

// Поєднання Timestamped із структурою всієї сторінки
export type PageData = Timestamped & {
  title: string
  slug: string
  metaDescription?: string
  blocks: PageBlock[]
}
```

### 2.3.3. Дискриміноване об'єднання (Discriminated Union Types, оператор `|`)

Для типізації масиву блоків сторінки застосовано патерн Discriminated Union. Спільне поле `type` слугує дискримінатором, за яким компілятор TypeScript автоматично звужує тип (type narrowing) всередині блоків `switch`:

```typescript
export type PageBlock =
  | HeroBlock
  | WhyUsBlock
  | BenefitsBlock
  | ProductsShowcaseBlock
  | ReviewsBlock
  | FaqBlock
  | CtaBlock
```

Також об'єднання типів використано для суворого контролю стану асинхронного ресурсу:

```typescript
export type AsyncResource<T> =
  | { state: 'loading' }
  | { state: 'error'; message: string; retry: () => void }
  | { state: 'ready'; data: T }
```

### 2.3.4. Узагальнені типи (Generics) та типізація функцій

Для стандартизації роботи з API створено універсальний узагальнений тип `ApiResponse<T>`, що дозволяє типізувати будь-які відповіді бекенду:

```typescript
export type ApiResponse<T> = {
  data: T | null
  error: string | null
  status: number
  isFallback?: boolean
}

// Типізація функції рендерера із обмеженням дженеріка T extends BaseBlock
export type BlockRenderer<T extends BaseBlock> = (block: T) => string
```

Завдяки суворій типізації будь-яка спроба звернутися до неіснуючого поля блоку (наприклад, звернення до `block.stats` у блоці `faq`) блокується компілятором ще на етапі написання коду.

## 2.4. Деплой та контрольний приклад: розгортання проєкту, оформлення репозиторію (README.md), контрольний приклад із скріншотами (редактор в CMS, відвідувач на сайті, обробка помилок)

### 2.4.1. Розгортання проєкту на Vercel та інтеграція з Neon

Процес розгортання fullstack-додатка складався з таких кроків:

1. **Створення хмарної БД Neon**:
   - На платформі Neon зареєстровано проєкт `liorashop-dev` у регіоні Франкфурт (`eu-central-1`).
   - Активовано режим **Connection Pooling** для отримання адреси пулу:  
     `postgresql://liorashop_owner:***@ep-***-pooler.eu-central-1.aws.neon.tech/neondb?sslmode=require`.
2. **Публікація репозиторію на GitHub**:
   - Локальний репозиторій ініціалізовано командою `git init`.
   - Файли `.env`, `.env.local` та директорії `node_modules/`, `.next/`, `dist/` внесено до `.gitignore`.
   - Здійснено коміт та відправку коду у гілку `main` віддаленого репозиторію.
3. **Налаштування хостингу на Vercel**:
   - Створено окремий проєкт для CMS із параметром **Root Directory** = `cms`. У налаштування середовища (Environment Variables) додано змінні `DATABASE_URL` та `PAYLOAD_SECRET`.
   - Створено проєкт для фронтенду з **Root Directory** = `frontend` та вказано змінну `VITE_API_URL` з адресою задеплоєної CMS.

### 2.4.2. Контрольний приклад та сценарії тестування

Працездатність розробленої системи перевірено на трьох основних сценаріях:

#### Сценарій 1. Початковий екран вибору ролі та перегляд промо-лендінгу відвідувачем
При завантаженні сайту відображається модальне вікно вибору:
- При виборі «Я Користувач» застосунок плавно відкриває промо-лендінг.
